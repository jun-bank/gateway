# PR #5 — 이미지 발행 전 테스트: 발행 관문

이 문서는 gateway CI에 테스트 스텝이 들어간 경위를 다룬다. 별도 이슈 없이 처리된 작은 PR이지만, "깨진 코드의 이미지가 배포 경로에 올라갈 수 있다"는 구멍을 막은 변경이고, 블루-그린 PR(#2)의 리뷰가 남긴 잔여 목록에서 온 것이다.

## 문제와 원인

PR 본문이 인과를 한 문장으로 적었다: "지금은 docker build만 해서 깨진 코드의 이미지가 GHCR에 올라가고 배포-agent가 그 digest를 집어갈 수 있다." 원인은 빌드 구조에 있다 — Dockerfile의 빌드 스테이지는 `bootJar`만 만들고 테스트를 실행하지 않는다. CI 잡에도 테스트 스텝이 없으니, 어디에서도 테스트가 돌지 않은 채 이미지가 발행되고, 그 이미지는 CD를 통해 자동으로 배포 요청이 된다. PR #2에서 만든 21건의 테스트가 정작 배포 경로를 지키지 못하는 상태였다.

## 채택 — 스텝 순서 자체가 보증 수단

GitHub Actions의 스텝은 순차 실행이고 실패하면 잡이 중단된다. 그래서 테스트를 GHCR 로그인·빌드·push **앞에** 두면, 별도 게이트나 조건문 없이 이미지가 발행되는 경로 자체가 사라진다. 그 논리가 주석에 그대로 있다:

```yaml
# .github/workflows/build.yml:21-33 (발췌)
# 테스트를 이미지 빌드보다 **먼저** 돌린다.
# Dockerfile 의 빌드 스테이지는 bootJar 만 만들 뿐 테스트를 실행하지 않으므로,
# 이 스텝이 없으면 깨진 코드로 만든 이미지가 그대로 GHCR 에 push 되고
# 배포-agent 가 그 digest 를 집어간다(ADR-027). 스텝은 순차 실행이고 실패 시
# 잡이 중단되므로, 여기서 막으면 이미지 자체가 발행되지 않는다.
- name: 테스트
  run: ./gradlew --no-daemon test
```

비용도 채택 시점에 기록됐다 — 컴파일이 2회(테스트용 + Docker 빌드용) 돌아 잡 시간이 는다. 이 잔여가 나중에 이슈 #7("CI 정비 — 빌드 1회화·wrapper 검증")로 이슈화됐다.

## 검증 — UP-TO-DATE 함정

검증에서 눈여겨볼 것은 그린 위장 자가 점검이다. Gradle은 입력이 안 바뀌면 테스트를 캐시로 건너뛰고 성공을 보고할 수 있다(UP-TO-DATE). 그래서 로컬 확인을 `--rerun-tasks`로 강제 재실행해, "통과했다"가 "실제로 돌았다"인지를 확인했다. 이 변경의 계약은 스텝 순서 그 자체이므로, YAML 파싱과 순서 확인(checkout → JDK 21 → test → 로그인 → 빌드·push)이 검증의 본체다.
